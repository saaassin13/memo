# AI 辅助 App 开发最佳实践指南

> 基于备忘录 App (时光序) 完整开发过程总结，涵盖 18 个步骤、8 个功能模块的实战经验。

---

## 一、开发流程总览

```
产品调研 → 页面设计 → 架构设计 → 脚手架搭建 → 功能迭代（设计→开发→集成） → 视觉优化
```

### 推荐的 5 阶段流程

| 阶段 | 产出物 | 耗时占比 | 关键原则 |
|------|--------|----------|----------|
| **Phase 0: 调研** | 竞品分析 + 功能清单 | 5% | 确定 MVP 范围，区分核心/差异化/辅助功能 |
| **Phase 1: 设计** | 页面结构 + 技术架构 | 15% | 前置所有数据模型和数据库 Schema |
| **Phase 2: 骨架** | 可运行的空壳项目 | 10% | 一次性搭建所有基础设施（路由、数据库、主题） |
| **Phase 3: 迭代** | 逐个功能的设计+开发 | 60% | 严格的 设计→开发→集成 循环 |
| **Phase 4: 打磨** | 视觉升级 + 体验优化 | 10% | 功能完成后再统一优化视觉风格 |

## 二、任务分解方法论

### 2.1 三层分解法

```
第 1 层：功能模块（Feature）
  └─ 第 2 层：开发阶段（Phase）
       └─ 第 3 层：具体任务（Task）
```

**示例：纪念日功能**
```
Feature: 倒数纪念日
  ├── Phase 1: 数据层（实体 + 表 + 仓库）
  ├── Phase 2: 状态管理（Providers）
  ├── Phase 3: 列表页 UI
  ├── Phase 4: 编辑页 UI
  ├── Phase 5: 农历工具类
  └── Phase 6: 集成（导航 + 日历联动）
```

### 2.2 设计文档模板

每个功能的**设计步骤**应包含以下固定结构：

```markdown
# [功能名] 设计

## 1. 功能概述（一句话说清楚做什么）
## 2. 页面布局（ASCII 画出界面结构）
## 3. 模块拆解（表格列出每个区域的组件和交互）
## 4. 数据模型（Entity 定义 + 字段说明）
## 5. 数据库 Schema（建表 SQL）
## 6. Provider 设计（状态管理方案）
## 7. 视觉规范（颜色、间距、圆角、阴影）
## 8. 文件清单（需要创建/修改的文件列表）
## 9. 开发步骤（编号的子任务清单）
```

### 2.3 开发文档模板

每个功能的**开发步骤**应包含：

```markdown
# [功能名] 开发

## 完成情况
- [x] Phase 1: 数据层
- [x] Phase 2: 状态管理
- [x] Phase 3: 主页面
- [ ] Phase 4: 编辑页面

## 已创建文件
- lib/domain/entities/xxx.dart ✅
- lib/data/database/tables/xxx.dart ✅

## 已修改文件
- lib/data/database/database.dart（新增表）

## 已知问题
- [ ] 导航返回时状态未刷新
```

## 三、关键技术决策（经验验证）

### 3.1 架构选型

| 决策点 | 选择 | 原因 | 事后评价 |
|--------|------|------|----------|
| 架构模式 | Clean Architecture (3层) | 职责分离，利于 AI 分步生成代码 | **验证正确** - 每层独立生成，无耦合问题 |
| 状态管理 | Riverpod | 编译安全，Provider 组合灵活 | **验证正确** - StreamProvider 处理数据库流非常自然 |
| 路由 | GoRouter + StatefulShellRoute | 声明式，支持底部导航多 Tab | **验证正确** - Tab 状态保持无问题 |
| 本地存储 | Drift (SQLite) | 类型安全，自动生成 DAO | **验证正确** - Schema 迁移 (v4→v5→v6) 流程清晰 |

### 3.2 数据库设计策略

**核心经验：前量所有数据模型**

```dart
// Step 2 一次性定义所有 8 个实体，而非边做边加
Memos, Todos, Diaries, Anniversaries,
Countdowns, Accounts, Goals, Weights
```

**好处：**
- 后续功能开发只需关注 UI 和业务逻辑，无需回头改 Schema
- 日历页面（集成点）可以提前规划数据聚合方式
- 避免频繁的数据库迁移

**迁移策略：**
```
v1 → 初始 7 张表
v4 → 扩展日记字段（mood, labels）
v5 → 扩展体重字段（bodyFat, exercise 等 5 个新字段）
v6 → 扩展用户设置字段
```

### 3.3 功能开发顺序

```
推荐顺序（本项目验证）：

1. 备忘录（基础 CRUD，建立模式）
   ↓
2. 待办（复用备忘录的分类组件模式）
   ↓
3. 日历（集成 Todo + Memo，验证数据聚合方案）
   ↓
4. 纪念日（引入农历等工具类）
   ↓
5. 日记（日历视图 + 自动保存模式）
   ↓
6. 体重（最复杂：统计图表 + Canvas 绘制）
   ↓
7. 我的（聚合所有数据的 Dashboard）
```

**关键原则：**
- 先做**简单 CRUD** 功能，建立开发模式
- 再做**集成型**功能（日历），验证跨模块方案
- 复杂功能（体重统计）放在模式成熟后
- Dashboard 类功能（我的）最后，因为它读取所有其他模块

## 四、设计与开发分离的最佳实践

### 4.1 为什么必须分离

| 方面 | 设计步骤 | 开发步骤 |
|------|----------|----------|
| 关注点 | **做什么、长什么样** | **怎么实现** |
| 产出物 | ASCII 布局 + 视觉规范 + 数据模型 | 代码文件 + 状态标记 |
| 评审标准 | 交互是否合理、视觉是否一致 | 功能是否完成、代码是否正确 |
| 修改成本 | 改设计便宜 | 改实现昂贵 |

### 4.2 设计文档的质量标准

好的设计文档应该让开发者（或 AI）**无需提问就能直接实现**：

- [ ] 布局用 ASCII 画出，标注每个区域的内容
- [ ] 颜色使用 Hex 值，不使用描述性词汇
- [ ] 间距使用具体 dp 值（如 16dp, 12dp）
- [ ] 数据模型定义到字段级别，含类型和约束
- [ ] 交互流程用文字描述清楚，含动画参数（时长、缓动）
- [ ] 复杂逻辑用伪代码或自然语言描述算法

### 4.3 开发步骤的执行原则

- **严格按 Phase 顺序执行**：数据层 → 状态层 → UI 层 → 集成层
- **每完成一个 Phase，立即更新文档状态**
- **遇到设计遗漏，回到设计文档补充，而不是临时拍脑袋**

## 五、Prompt 编写技巧

### 5.1 设计步骤的 Prompt 模板

```
请为 [功能名] 编写详细的设计文档，包含：
1. ASCII 页面布局图
2. 每个区域的组件拆解（表格）
3. 数据模型定义（字段名、类型、说明）
4. Drift 数据库表定义
5. Riverpod Provider 设计
6. 视觉规范（颜色、间距、圆角）
7. 需要创建和修改的文件清单
8. 开发步骤编号清单

视觉风格参考：[描述或引用之前的设计风格]
数据模型扩展基础：[引用现有 Entity 或表]
```

### 5.2 开发步骤的 Prompt 模板

```
请按照以下设计文档实现 [功能名]：

[粘贴完整设计文档]

开发要求：
1. 严格按照 Phase 顺序：数据层 → Providers → UI → 集成
2. 每完成一个文件，在文档中标记 ✅
3. 如果需要修改已有文件，说明修改内容
4. 遇到设计不清晰的地方，列出问题清单
5. 代码风格遵循项目已有模式（参考 [类似功能文件路径]）
```

### 5.3 提升 AI 输出质量的关键技巧

| 技巧 | 示例 | 效果 |
|------|------|------|
| **引用已有代码模式** | "参考 memo_providers.dart 的 StreamProvider 写法" | 输出风格一致，减少返工 |
| **提供具体约束** | "使用 Material 3，不引入新依赖" | 避免不兼容的技术选型 |
| **指定文件路径** | "创建 lib/presentation/providers/diary_providers.dart" | 避免文件命名混乱 |
| **分步骤执行** | "先只实现数据层，等我确认后再做 UI" | 便于中间纠错 |
| **提供上下文** | 粘贴相关已有文件内容 | AI 不需要猜测现有代码结构 |

## 六、踩坑与经验教训

### 6.1 需要避免的问题

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| **视觉风格不一致** | 每个功能独立设计，缺乏统一规范 | 先在 Step 4 建立视觉 Design System，后续引用 |
| **数据库频繁迁移** | 一开始没想清楚所有字段 | 前置所有数据模型（本项目已验证） |
| **功能做了一半发现设计有问题** | 设计文档不充分 | 设计文档必须包含伪代码级的逻辑描述 |
| **组件无法复用** | 每个功能从零写 UI | 建立 `widgets/` 公共组件库，设计时就规划复用 |
| **导航状态丢失** | 路由配置不正确 | 使用 StatefulShellRoute 保持 Tab 状态 |

### 6.2 做对了的事情

| 实践 | 收益 |
|------|------|
| Clean Architecture 分层 | AI 可以分层生成代码，每次只需关注一层 |
| 所有数据模型前置定义 | 后期功能开发几乎不用改 Schema |
| 设计与开发严格分离 | 开发时零歧义，减少来回沟通 |
| 日历作为集成点 | 验证了跨模块数据聚合方案 |
| 体重功能之后做 | 复杂的 Canvas 图表在模式成熟后更容易实现 |
| 最后做"我的"页面 | 此时所有数据源都已就绪 |

### 6.3 可以改进的地方

| 改进点 | 建议 |
|--------|------|
| 缺少测试 | 在每个功能的开发步骤中加入单元测试任务 |
| 视觉 Design System 后置 | 应在 Step 4 就建立完整的组件样式库 |
| 未使用的模块（记账/目标/倒数） | 在 Step 1 就应该砍掉不在 MVP 范围内的功能 |
| 动画过度指定 | 让开发阶段决定具体参数，设计阶段只描述交互意图 |
| 导出/导入功能搁置 | 提前评估技术难度，要么 MVP 内做，要么明确不做 |

- 设计文件总是奇数编号，开发文件紧跟其后

## 八、新项目的快速启动清单

开始新项目时，按此清单执行：

### Phase 0: 调研（1-2 轮对话）
- [ ] 列出核心功能、差异化功能、辅助功能
- [ ] 确定 MVP 范围（砍掉不在 MVP 内的功能）
- [ ] 输出 `00-product-requirements.md`

### Phase 1: 设计（2-3 轮对话）
- [ ] 设计全局页面结构（底部导航 + 所有页面）
- [ ] 选择技术栈（框架、状态管理、路由、存储）
- [ ] 定义**所有**数据模型和数据库 Schema
- [ ] 输出 `01-page-design.md` + `02-architecture.md`

### Phase 2: 骨架（1-2 轮对话）
- [ ] 创建项目，配置依赖
- [ ] 搭建 Clean Architecture 目录结构
- [ ] 实现所有数据库表和仓库接口
- [ ] 配置路由和底部导航
- [ ] 建立 Design System（颜色、字体、公共组件）
- [ ] 输出 `03-scaffold-progress.md` + `04-design-system.md`

### Phase 3: 功能迭代（每个功能 2 轮对话）
对每个 MVP 功能：
- [ ] 第 1 轮：编写设计文档（引用 Design System）
- [ ] 第 2 轮：实现开发（引用设计文档 + 已有代码模式）
- [ ] 完成后更新进度文档

### Phase 4: 打磨（1-2 轮对话）
- [ ] 统一视觉风格
- [ ] 优化交互体验
- [ ] 补充边界情况处理

## 九、AI 协作核心原则

1. **一次只做一件事** — 每轮对话聚焦一个步骤（设计 OR 开发，不是两者）
2. **上下文即权力** — 提供的代码和文档越详细，AI 输出质量越高
3. **先画图再写代码** — 设计文档是 AI 的"施工图纸"，没有图纸不要开工
4. **模式先行** — 第一个功能建立模式，后续功能复用模式
5. **进度可见** — 每个开发文档都用 checklist 追踪进度
6. **分离关注点** — 数据层、逻辑层、UI 层分开处理
7. **不要跳步** — 严格按 需求→设计→开发→测试 的顺序执行
